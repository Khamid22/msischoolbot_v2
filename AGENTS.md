# MSI School Project Rules For Coding Agents

Read this before editing the project. Keep changes small, verify them, and do
not guess across architectural boundaries.

## Non-Negotiable Data Safety

- Never delete PostgreSQL rows or values.
- Never run destructive SQL such as `DELETE`, `TRUNCATE`, `DROP TABLE`, or
  broad `UPDATE` statements unless the user explicitly approves the exact SQL.
- Database cleanup means normalize or add missing values, not remove data.
- Before any data migration, produce a preview query and a backup/snapshot plan.
- Built frontend files may be regenerated. PostgreSQL data must not be treated
  as disposable generated output.

## Current Architecture

```text
shared/          Python logic and database access shared by bot and web
tgbot/           Telegram bot only
web/backend/     Flask backend only
web/frontend/    React frontend only
```

Dependency direction:

```text
web/frontend -> web/backend -> shared -> shared/db -> PostgreSQL
tgbot -----------------------> shared -> shared/db -> PostgreSQL
```

Forbidden imports:

- `tgbot` must not import `web.backend`.
- `web.backend` must not import `tgbot`.
- `web/frontend` must not import Python code.
- `shared` must not import Flask, aiogram, or React/frontend code.

## What To Touch

Use this map before editing:

| Task | Touch |
|---|---|
| Telegram command, bot message, bot button | `tgbot/handlers/`, `tgbot/keyboards/`, `tgbot/helpers.py` |
| Shared login/account logic used by bot and web | `shared/identity/` |
| Subject/date/school canonical rules | `shared/academics/` |
| PostgreSQL connection/schema/query helpers | `shared/db/` |
| Flask auth/session/routes/API composition | `web/backend/` |
| Role-specific backend workflows | `web/backend/roles/<role>/` |
| Reusable backend school domains | `web/backend/domains/<domain>/` |
| React app boot/page routing | `web/frontend/src/app/` |
| Reusable React UI and browser helpers | `web/frontend/src/shared/` |
| Role-specific React screens | `web/frontend/src/roles/<role>/` |

## What Not To Touch Casually

- Do not manually edit `web/backend/static/react/`; it is generated by
  `cd web/frontend && npm run build`.
- Do not add new source files under old frontend paths such as
  `web/frontend/src/pages`, `web/frontend/src/components`,
  `web/frontend/src/lib`, or `web/frontend/src/hooks`.
- Do not recreate old root shims like `shared/auth.py`,
  `shared/canonical.py`, or `shared/subject_summary.py`.
- Do not add new code to legacy backend top-level role folders if the matching
  `web/backend/roles/<role>/` or `web/backend/domains/<domain>/` owner exists.
- Do not rename database columns or route parameters in bulk. Some old names
  still represent public URL contracts.

## Frontend Rules

The React source tree should stay like this:

```text
web/frontend/src/
├── app/
├── shared/
│   ├── lib/
│   └── ui/
└── roles/
    ├── admin/
    ├── parent/
    └── student/
```

- Put role screens in `roles/<role>/pages`.
- Put admin tabs/panels in `roles/admin/panels`.
- Put reusable visual components in `shared/ui`.
- Put browser-only helpers in `shared/lib`.
- Keep mobile navigation as overlay sidebars opened by toggles.
- Use `overflow-x-auto` for wide tables or dense panels on mobile.

## Backend Rules

Inside `web/backend`:

- `roles/` answers: what does this type of user do?
- `domains/` answers: what business area is this about?
- If logic is needed by both bot and web, move it to `shared/`.
- If SQL is reused, put it under `shared/db/queries/` or
  `shared/db/cross_queries/`.
- Keep Flask request/session/Blueprint logic out of `shared/`.

## Naming Rules

Use `docs/GLOSSARY.md` for names. Most important:

- `student_code` means login code like `MSI00001`.
- `student_row_id` means `students.id`.
- `enrollment_id` means the imported/public dashboard id used by old URLs.
- `telegram_user_id` means the numeric Telegram user id.
- `subject_name`, `subject_short`, and `subject_key` are different concepts.

Do not use vague names like `student_id`, `user_id`, or `id` across service
boundaries unless the meaning is obvious from the local database row.

## Verification Commands

Run the smallest relevant set before reporting success.

Backend/import check:

```bash
python3 -m compileall -q shared tgbot web/backend scripts main.py
python3 - <<'PY'
from web.backend.server import app
print(app.name)
PY
```

Frontend check:

```bash
cd web/frontend
npm run check-types
npm run build
```

Stale import scan examples:

```bash
rg "from tgbot|import tgbot" web/backend shared
rg "from web.backend|import web.backend" tgbot shared
rg "@/pages|@/components|@/lib|@/hooks|src/pages|src/components" web/frontend/src
```

Duplicate Python/TypeScript scan:

```bash
find shared web/backend tgbot scripts -name '*.py' -type f -print0 \
  | xargs -0 shasum | sort \
  | awk 'seen[$1]{print prev[$1]"\n"$0"\n"} {seen[$1]=1; prev[$1]=$0}'

find web/frontend/src -type f \( -name '*.ts' -o -name '*.tsx' \) -print0 \
  | xargs -0 shasum | sort \
  | awk 'seen[$1]{print prev[$1]"\n"$0"\n"} {seen[$1]=1; prev[$1]=$0}'
```

## Feature Workflow

Before implementing a feature, identify:

1. The role: student, parent, admin, teacher, CEO, customer support, or owner.
2. The domain: academics, identity, payments, resources, announcements,
   complaints, people, or communication.
3. The data source: existing query, new query, or new table/column.
4. The UI surface: role page, panel, shared component, or Telegram message.
5. The verification command.

If a change crosses multiple layers, work in this order:

```text
shared/db -> shared/domain rules -> web/backend -> web/frontend or tgbot
```

## Debug Workflow

Debug in layers:

1. Is the data present in PostgreSQL?
2. Does the `shared/db` query return it?
3. Does the backend service/API return it?
4. Does the frontend or bot receive it?
5. Does the UI/message render it correctly?

Do not start by editing random UI or query files. Search first with `rg`.
