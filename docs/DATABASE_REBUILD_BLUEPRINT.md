# MSI School Database Rebuild Blueprint

This is the target database shape for the clean FastAPI system.

The current local database has 39 tables. The biggest issue is not just table
count; it is overlapping ownership:

- staff accounts live in `admins`, while teacher auth lives in `teacher_auth`
- parents exist in `admins`, `parents`, `parent_children`, and `parent_student_links`
- subjects are repeated per school in `academic_subjects`
- imported gradebook data is split across old import tables and newer academic tables
- curriculum exists, but groups and lessons are not yet cleanly generated from a program

The rebuild should make MSI the center:

```text
MSI offers subject programs -> client schools use them -> groups run those programs
students enroll in groups -> parents link to students -> staff manage by role/scope
```

## Exact Target Table Count

Target: **34 production tables**.

This is enough for the actual business model without keeping old duplicate
tables around.

## 1. Identity And Access

### 1. `msi_staff`

One row per internal staff member.

Purpose:

- CEO
- academic director
- head of department
- customer support
- admin/owner
- teacher login can also be linked here if we want teachers to use staff access

Important fields:

- `id`
- `login`
- `password_hash`
- `display_name`
- `phone`
- `telegram_user_id`
- `telegram_username`
- `role`
- `status`
- `subject_scope`
- `school_scope`
- `created_at`
- `updated_at`

Notes:

- `role` can be `owner`, `ceo`, `academic_director`, `head_of_department`,
  `customer_support`, `admin`, `teacher`.
- `subject_scope` handles Head of Math, Head of English, etc.
- `school_scope` handles staff limited to one client school if needed.

### 2. `telegram_accounts`

One Telegram identity, reusable across parent/student/staff.

Important fields:

- `telegram_user_id`
- `username`
- `first_name`
- `last_name`
- `linked_entity_type`
- `linked_entity_id`
- `created_at`
- `updated_at`

### 3. `account_invites`

Temporary links generated by staff for parents or students.

Important fields:

- `id`
- `token_hash`
- `invite_type`
- `target_type`
- `target_id`
- `issued_by_staff_id`
- `expires_at`
- `used_at`
- `telegram_user_id`
- `created_at`

### 4. `audit_events`

Who changed what and when.

## 2. Client Schools, Students, Parents

### 5. `schools`

Client schools, not MSI internal departments.

### 6. `students`

One row per student/person.

Important fields:

- `id`
- `student_code` such as `MSI00001`
- `full_name`
- `school_id`
- `telegram_user_id`
- `profile_description`
- `photo_url`
- `status`
- `created_at`
- `updated_at`

### 7. `student_auth`

Optional login/password for student web access.

This can stay separate so Telegram mini app access can work without passwords.

### 8. `student_telegram_links`

Telegram mini app links for students.

This stays separate from `student_auth` because Telegram access and web
password access are different ways to enter the same student account.

### 9. `parents`

One row per parent/guardian.

Important fields:

- `id`
- `display_name`
- `phone`
- `telegram_user_id`
- `telegram_username`
- `preferred_language`
- `created_at`
- `updated_at`

No email by default. Parents in Tashkent mostly use phone/Telegram.

### 10. `parent_student_links`

Many-to-many parent/student link.

## 3. Subjects, Programs, Groups

### 11. `subjects`

Universal MSI subject catalog.

Examples:

- IGCSE Mathematics A
- English as a Second Language
- IGCSE Chemistry
- IGCSE Biology
- IGCSE Physics

Important fields:

- `id`
- `subject_key`
- `subject_name`
- `subject_short`
- `status`

### 12. `subject_programs`

Versioned scheme of work for a subject.

Example:

- `IGCSE Mathematics A / 2025-26 / IG Teaching Hubs MathsA SOW.xlsx`

### 13. `subject_program_items`

Lessons and exams from the scheme of work.

Important fields:

- `program_id`
- `item_order`
- `item_type` (`lesson`, `exam`)
- `title`
- `term_label`
- `week_label`
- `book_pages`
- `specification_points`

### 14. `groups`

Actual teaching groups/classes.

Important fields:

- `school_id`
- `program_id`
- `group_name`
- `group_code`
- `start_date`
- `end_date`
- `status`

### 15. `group_students`

Student enrollment in a group.

### 16. `teachers`

Teacher profile.

### 17. `teacher_subjects`

Which subjects a teacher can teach.

### 18. `group_teachers`

Which teachers are assigned to which group.

### 19. `group_schedule_rules`

Repeating schedule rules.

Example:

- Monday and Wednesday
- 15:00 to 16:30
- Room 304

### 20. `lesson_sessions`

Generated lesson calendar from group schedule + subject program.

## 4. Gradebook

### 21. `attendance_records`

Per student, per lesson session.

Values:

- `present`
- `absent`
- `justified`

### 22. `homework_scores`

AAP/HW scores on the 1-9 scale.

### 23. `exam_results`

Exam scores on the 1-9 scale unless a future subject uses a different scale.

### 24. `coin_events`

Student reward/coin history.

## 5. Resources

### 25. `resource_types`

Video, worksheet, practice sheet, past paper, homework, etc.

### 26. `resources`

Uploaded or linked learning materials.

## 6. Communication

### 27. `announcements`

School/MSI announcements.

### 28. `support_tickets`

Parent complaint/support ticket.

### 29. `ticket_messages`

Threaded ticket messages.

Direct chat messages can be added later if we keep student/staff chat separate
from tickets. It is not part of the initial 34-table schema.

### 30. `payments`

Parent/student billing records.

## 7. Office Hours

### 31. `office_hour_slots`

Teacher availability.

### 32. `office_hour_bookings`

Student bookings.

## 8. System Settings

### 34. `app_settings`

Typed key/value settings for feature flags and deployment-safe configuration.

## Tables To Remove In A Rebuild

When the rebuild is approved, these current concepts should disappear:

- `admins` -> replaced by `msi_staff`
- `bot_users` -> replaced by `telegram_accounts`
- `academic_schools` -> `schools`
- `academic_subjects` -> universal `subjects`
- `academic_curriculum_programs` -> `subject_programs`
- `academic_curriculum_items` -> `subject_program_items`
- `academic_groups` -> `groups`
- `academic_enrollments` -> `group_students`
- `academic_lessons` and `lesson_catalog` -> `lesson_sessions`
- `academic_attendance_records` -> `attendance_records`
- `academic_homework_scores` -> `homework_scores`
- `academic_exam_results` -> `exam_results`
- `academic_coin_events` -> `coin_events`
- `parent_children` -> remove; keep only `parent_student_links`
- parent rows in `admins` -> remove; keep only `parents`
- `parent_complaints` -> `support_tickets`
- `parent_complaint_messages` -> `ticket_messages`
- `teacher_auth` -> `msi_staff` if teacher login is staff-style, otherwise a
  future `teacher_auth` table can be recreated cleanly
- `students_sheet_map` -> remove old Google Sheets mapping
- `subject_summaries` -> remove old imported summary cache
- `app_meta` -> replace with typed config later only if needed

## Required Rebuild Order

1. Backup current local and Railway PostgreSQL.
2. Create a new empty schema from the target tables.
3. Import subject programs from the five SOW Excel files.
4. Import schools.
5. Import students.
6. Import teachers.
7. Create groups using school + subject program.
8. Generate `lesson_sessions`.
9. Import gradebook/attendance/exams if needed from Excel.
10. Generate parent invite links instead of manually creating parent passwords.
11. Update code queries to the new table names.
12. Verify every workspace: CEO, Academic Director, Head of Department,
    Customer Support, Teacher, Student, Parent.

## Safety Rule

Do not run destructive SQL until the exact SQL file is reviewed and approved.
